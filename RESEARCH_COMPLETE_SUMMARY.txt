OFFICIAL LSP SETTINGS MECHANISM:

The Language Server Protocol 3.17 specification defines THREE distinct
configuration mechanisms that work at different stages of the LSP lifecycle:

┌─────────────────────────────────────────────────────────────────────────┐
│ LAYER 1: COMMAND-LINE ARGUMENTS (cmd)                                   │
├─────────────────────────────────────────────────────────────────────────┤
│ Timing:      T0 (when spawning the server process)                      │
│ Changeable:  NO (cannot change after process starts)                    │
│ Purpose:     Control HOW the server process is started                  │
│ Example:     cmd = { 'omnisharp', '--stdio' }                           │
│ LSP Field:   Not specified (OS/shell specific)                          │
│ Spec Ref:    Not defined in LSP (implementation detail)                 │
└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│ LAYER 2: INITIALIZATION OPTIONS (init_options)                          │
├─────────────────────────────────────────────────────────────────────────┤
│ Timing:      T2 (during the initialize request)                         │
│ Changeable:  NO (one-time only, during initialization)                  │
│ Purpose:     Provide server-specific STARTUP PARAMETERS                 │
│ Example:     init_options = { ... }                                     │
│ LSP Field:   InitializeParams.initializationOptions                     │
│ Type:        LSPAny (any valid JSON structure)                          │
│ Spec Ref:    LSP 3.17 - Initialize Request section                      │
└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│ LAYER 3: RUNTIME SETTINGS (settings)                                    │
├─────────────────────────────────────────────────────────────────────────┤
│ Timing:      T5+ (AFTER the initialized notification)                   │
│ Changeable:  YES (can be updated dynamically without restart)           │
│ Purpose:     Provide DYNAMIC server CONFIGURATION                       │
│ Example:     settings = { omnisharp = { enableRoslynAnalyzers = true }} │
│ LSP Mech:    workspace/didChangeConfiguration notification              │
│ Type:        LSPAny (any valid JSON structure)                          │
│ Spec Ref:    LSP 3.17 - Workspace Features section                      │
└─────────────────────────────────────────────────────────────────────────┘

CRITICAL INSIGHT:
─────────────────

Settings are NOT sent in the initialize request!

The LSP specification explicitly separates configuration into two phases:

  1. Initialization (T2): initializationOptions sent during initialize
  2. Configuration (T5+): settings sent via workspace/didChangeConfiguration
                         AFTER the initialized notification

This design allows:
  ✓ Dynamic configuration updates
  ✓ Server restart-free configuration changes
  ✓ Client notification-based configuration management
  ✓ Compliance with LSP specification

==============================================================================
                         COMPLETE TIMELINE
==============================================================================

EVENT                          TIMING  LSP MESSAGE/ACTION    SETTINGS APPLIED
──────────────────────────────────────────────────────────────────────────
Process spawned                T0      (OS process create)   cmd args (--stdio)
Server starts                  T1      (listening)           (none)
Initialize request sent        T2      initialize request    initializationOptions
Server processes init          T2.5    (server-side)         initializationOptions
Initialize response received   T3      initialize response   (capabilities stored)
Initialized notification sent  T4      initialized notif.    (none)
didChangeConfiguration sent    T5      didChangeConfiguration settings
Server processes config        T5.5    (server-side)         settings
Normal operation              T6+     (document messages)    All active

KEY TIMING RULES:
─────────────────

1. cmd args apply at T0 (process spawn) - FIXED
2. initializationOptions applied at T2.5 (server processes init) - FIXED
3. settings applied at T5.5 (server processes didChangeConfiguration) - DYNAMIC

Each layer is completely independent and applies at a different time.
They cannot be mixed or substituted.

                    OMNISHARP CORRECT CONFIGURATION
==============================================================================

Based on official LSP specification, here is the correct way to configure
OmniSharp in Neovim:

lspconfig.omnisharp.setup({

  -- LAYER 1: PROCESS CONTROL (T0)
  cmd = {
    vim.fn.expand('~/.local/share/nvim/mason/bin/OmniSharp'),
    '--stdio'           -- Required for LSP over stdin/stdout
  },

  -- LAYER 2: INITIALIZATION (T2)
  init_options = {
    -- Usually empty for OmniSharp
    -- Server startup parameters go here if needed
  },

  -- LAYER 3: RUNTIME CONFIGURATION (T5+)
  settings = {
    omnisharp = {
      -- Analyzer settings
      enableRoslynAnalyzers = true,
      enableEditorConfigSupport = true,
      enableReferenceCodeLens = true,

      -- Formatting settings
      organizeImportsOnFormat = true,
      enableImportCompletion = true,

      -- Code lens settings
      enableCodeLensOnMethods = true,
      enableCodeLensOnProperties = false,
      enableCodeLensOnFields = false,

      -- Diagnostics settings
      maxProjectFileCountForDiagnosticAnalysis = 1000,

      -- Logging (for debugging)
      loggingLevel = "information",  -- Set to "debug" for troubleshooting
    }
  }
})

==============================================================================
                    COMMON MISTAKES (DON'T DO THESE)
==============================================================================

MISTAKE 1: Putting settings in cmd
❌ WRONG:
   cmd = { 'omnisharp', '--enableRoslynAnalyzers=true' }

✓ CORRECT:
   settings = { omnisharp = { enableRoslynAnalyzers = true } }

MISTAKE 2: Putting dynamic settings in init_options
❌ WRONG:
   init_options = { enableRoslynAnalyzers = true }

✓ CORRECT:
   settings = { omnisharp = { enableRoslynAnalyzers = true } }

MISTAKE 3: Expecting settings to apply during initialization
❌ WRONG: Thinking settings apply during T2 (initialize)

✓ CORRECT: Settings apply at T5+ (after initialized notification)

MISTAKE 4: Using wrong setting key names
❌ WRONG:
   settings = { enableRoslynAnalyzers = true }

✓ CORRECT:
   settings = { omnisharp = { enableRoslynAnalyzers = true } }

MISTAKE 5: Not restarting LSP after configuration changes
❌ WRONG: Change config and expect it to work immediately

✓ CORRECT: Run `:LspRestart` or reload Neovim

                    BOTTOM LINE
==============================================================================

The Language Server Protocol specification clearly and explicitly defines
how settings should be passed to language servers through three separate,
non-interchangeable mechanisms:

1. COMMAND-LINE ARGUMENTS → control PROCESS startup (T0)
2. INITIALIZATION OPTIONS → configure SERVER startup (T2)
3. RUNTIME SETTINGS → enable DYNAMIC configuration (T5+)

Each mechanism applies at a different time in the LSP lifecycle.
Using the correct mechanism ensures:
  ✓ LSP specification compliance
  ✓ Compatibility with all LSP clients
  ✓ Compatibility with all LSP servers
  ✓ Proper timing of configuration application
  ✓ Support for dynamic configuration changes

This research provides complete, official documentation for implementing
correct LSP configuration in Neovim and other editors.

Question 1: How does the flatten() function in on_new_config work?
─────────────────────────────────────────────────────────────────

Answer: Recursive table traversal that converts nested Lua tables to 
        colon-delimited command-line arguments

Location: nvim-lspconfig/lua/lspconfig/server_configurations/omnisharp.lua
          Lines ~58-70 (within on_new_config function)

Algorithm:
  1. For each key-value pair in table
  2. If value is table → recursively flatten and prepend key with ':'
  3. If value is scalar → format as key=value
  4. Nil values skipped (not in pairs() iteration)
  5. Boolean values converted to strings via vim.inspect()

Example:
  Input:  {RoslynExtensionsOptions = {EnableAnalyzersSupport = true}}
  Output: ["RoslynExtensionsOptions:EnableAnalyzersSupport=true"]

Complete Source Code:
  local function flatten(tbl)
    local ret = {}
    for k, v in pairs(tbl) do
      if type(v) == 'table' then
        for _, pair in ipairs(flatten(v)) do
          ret[#ret + 1] = k .. ':' .. pair
        end
      else
        ret[#ret + 1] = k .. '=' .. vim.inspect(v)
      end
    end
    return ret
  end

Key Behaviors:
  ✓ Handles arbitrary nesting depth
  ✓ Recursively processes one level at a time
  ✓ Prepends parent key when returning from recursion
  ✓ nil values skipped (not included in output)
  ✓ Boolean true/false converted to strings

Question 2: What format does OmniSharp expect for settings on command line?
───────────────────────────────────────────────────────────────────────────

Answer: Colon-delimited configuration arguments following OmniSharp's 
        internal configuration schema

Format: ParentKey:ChildKey=value

Examples:
  RoslynExtensionsOptions:EnableAnalyzersSupport=true
  RoslynExtensionsOptions:EnableImportCompletion=true
  RoslynExtensionsOptions:AnalyzeOpenDocumentsOnly=false
  FormattingOptions:EnableEditorConfigSupport=true
  FormattingOptions:OrganizeImports=true
  Sdk:IncludePrereleases=true
  DotNet:enablePackageRestore=false

Requirements:
  ✓ PascalCase for property names (NOT snake_case)
  ✓ Values as strings: "true", "false", "42"
  ✓ Colon (:) as nesting delimiter (NOT dot)
  ✓ Each argument is separate command-line parameter

OmniSharp Parsing Process:
  1. Parse command-line arguments from process startup
  2. Split on ':' for nested configuration
  3. Build configuration object
  4. Merge with omnisharp.json and defaults
  5. Command-line args have HIGHEST priority (override all)

Configuration Precedence (lowest to highest):
  1. Hardcoded defaults
  2. ~/.omnisharp/omnisharp.json (global)
  3. ~/project/omnisharp.json (project-level)
  4. Environment variables
  5. Command-line arguments ← HIGHEST (from on_new_config)

Detailed Explanation: See OMNISHARP_ON_NEW_CONFIG_TIMING_DETAILED.md


Question 3: Why might RoslynExtensionsOptions be empty in :LspInfo 
            but present in config?
──────────────────────────────────────────────────────────────────

Answer: :LspInfo displays the settings table AS CONFIGURED, not as applied.
        The settings are actually being passed as command-line arguments
        (flattened by flatten()), which :LspInfo doesn't display.

When :LspInfo shows:
  RoslynExtensionsOptions = {}

This does NOT necessarily mean settings weren't applied!

The settings are passed as command-line arguments like:
  RoslynExtensionsOptions:EnableAnalyzersSupport=true
  RoslynExtensionsOptions:EnableImportCompletion=true
  RoslynExtensionsOptions:AnalyzeOpenDocumentsOnly=false

:LspInfo doesn't show this flattened form.

Real Verification:
  $ ps aux | grep omnisharp | grep -v grep
  
  If output contains: RoslynExtensionsOptions:EnableAnalyzersSupport=true
  THEN: Settings ARE applied ✓

Root Causes (if TRULY empty):

  Cause 1: Settings not defined
    omnisharp = {
      settings = {}  ← Empty! No nested tables
    }
  Fix: Define RoslynExtensionsOptions and other tables

  Cause 2: servers.omnisharp out of scope
    local servers = { ... }  ← Local scope
    require('lspconfig').omnisharp.setup(servers.omnisharp)
    -- servers dies here, on_new_config can't access it later
  Fix: Define servers at module level

  Cause 3: Multiple setup() calls
    require('lspconfig').omnisharp.setup(config1)  ✓ First call wins
    require('lspconfig').omnisharp.setup(config2)  ✗ Second ignored
  Fix: Use mason-lspconfig handler for single, controlled call

  Cause 4: Old OmniSharp process still running
    pkill -f omnisharp  ✗ Doesn't work - old process has old settings
  Fix: Kill all: pkill -f omnisharp, then restart Neovim

  Cause 5: Using deprecated configuration
    enable_roslyn_analyzers = true  ✗ Deprecated (April 2024)
  Fix: Use settings table with RoslynExtensionsOptions

Debugging Steps:

  Step 1: Check if settings table defined
    :lua print(vim.inspect(servers.omnisharp.settings))
    Should show your nested settings structure

  Step 2: Check if running process has settings
    $ ps aux | grep omnisharp | grep -v grep
    Should show flattened args like RoslynExtensionsOptions:...

  Step 3: Check client configuration
    :lua print(vim.inspect(vim.lsp.get_clients({name='omnisharp'})[1].config.settings))
    Should match Step 1

  Step 4: Check LSP logs
    $ tail ~/.local/state/nvim/lsp.log | grep -i RoslynExtensions
    Should show settings being passed

Question 4: Does on_new_config run before or after the server starts?
──────────────────────────────────────────────────────────────────────

Answer: BEFORE the server spawns. It runs at T0.5 (pre-spawn phase) 
        to build the complete command-line arguments with flattened settings.

Timeline with Precise Timing:

  T0     Neovim startup
         • Load init.lua
         • Register LSP servers via require('lspconfig').omnisharp.setup()
         • on_new_config callback registered (not called yet)

  T0.2   User opens file
         • User: :e UserController.cs
         • File type detected: csharp

  T0.25  LSP selection
         • Check: Is there an LSP for csharp?
         • Found: omnisharp
         • Decide: Attach LSP to buffer

  T0.5   ⭐️ on_new_config CALLED ⭐️
         THIS IS THE CRITICAL MOMENT
         
         Function execution:
         1. Copy base cmd array
         2. Append hard-coded args (-z, --hostPID, DotNet:..., --encoding, --languageserver)
         3. Flatten settings table
         4. Append flattened args to cmd
         5. Modify capabilities (disable workspace folders)
         6. Return modified config
         
         Result: cmd array now contains ALL arguments needed for OmniSharp

  T0.6   Process spawn
         • vim.fn.jobstart(cmd_with_all_args)
         • OmniSharp child process starts
         • Parses command-line arguments
         • Loads configuration from CLI args (HIGHEST priority)
         • Initializes Roslyn analyzers

  T1     LSP Initialize request
         • Neovim sends: { method: "initialize", params: {...} }
         • Note: initializationOptions are IGNORED by OmniSharp
         • (Settings already applied from command-line args)

  T2     Initialize response
         • OmniSharp responds with capabilities

  T3     Initialized notification
         • Neovim sends: { method: "initialized", params: {} }

  T4+    Normal operation
         • Document opened (textDocument/didOpen)
         • Diagnostics published (textDocument/publishDiagnostics)
         • Analyzer warnings visible ✓

When on_new_config Runs Again:

  on_new_config is called again in these scenarios:

  Scenario 1: User runs :LspRestart
    :LspRestart
    ├─ Kill old OmniSharp process
    ├─ Call on_new_config with current config
    └─ Respawn with new settings ✓

  Scenario 2: Open C# file in new Neovim instance
    nvim file2.cs (different terminal/window)
    ├─ New Neovim loads init.lua
    ├─ Call on_new_config
    └─ New LSP instance with new settings

  Scenario 3: Source init.lua and :LspRestart
    :source ~/.config/nvim/init.lua
    :LspRestart
    └─ New settings applied ✓

When on_new_config does NOT run:

  ✗ Changing init.lua without :source or :LspRestart
  ✗ Opening another C# file in same buffer (uses existing connection)
  ✗ Reloading module without restarting LSP

Critical Implication:

  Settings are FROZEN at T0.5 when on_new_config runs
  They are embedded in command-line arguments passed to the process
  The process never re-reads the command line after startup
  
  Therefore:
    ✓ Settings apply reliably at startup
    ✓ OmniSharp receives them 100%
    ✓ They override omnisharp.json
    ✗ They cannot change without process restart (:LspRestart)
    ✗ Changing init.lua requires :LspRestart to apply
    ✗ No dynamic configuration updates (unlike some LSP servers)
